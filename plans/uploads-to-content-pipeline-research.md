# Research Report: Connecting Uploaded Files to the Content Pipeline (Step U0)

## Recommendation

**Choose Option A (a first-class `"Uploaded File"` `ContentSourceType` + push-ingest helper in `@memberjunction/content-pipeline`).** In MemberJunction's new Content Pipeline (`PR #4744`), `ExtractStage` already reads `MJ: Content Items.FileID` first via `tryExtractFromDurableFile` (`packages/ContentPipeline/engine/src/stages/ExtractStage.ts:138`, `314–342`) before consulting any source driver, and `SearchEngine.VerifyOriginRecords` (`packages/SearchEngine/src/generic/SearchEngine.ts:3183–3199`, `3240–3355`) plus Collaboration's three `"… In Reach"` RLS filters (`metadata/row-level-security-filters/.row-level-security-filters.json:422–451`) already enforce room, subtree, and `General`/`Team` band visibility through `MJ: Content Items.EntityRecordDocumentID → MJ: Entity Record Documents (EntityID, RecordID)`. The only missing piece is the 150-line bridge that creates/updates the `MJ: Entity Record Documents` row and `MJ: Content Items` row with `FileID` + `EntityRecordDocumentID` under a push-only `ContentSourceType` (`SupportsExhaustiveWalk = false`) and safely detaches `FileID` on delete so `DeleteContentItemStage.removeDurableCopy` (`packages/ContentPipeline/engine/src/stages/DeleteStage.ts:116–152`) does not destroy caller-owned `MJ: Files` rows still referenced by `MJ: Artifact Versions`. **Option B** requires a substantially larger MJ change because `AutotagEntity.Discover` (`packages/ContentAutotagging/src/Entity/generic/AutotagEntity.ts:537–591`) neither creates `MJ: Entity Record Documents` rows nor sets `EntityRecordDocumentID`, `WorkingRecordCommitter` (`packages/ContentPipeline/engine/src/WorkingRecordCommitter.ts:50`, `532–535`) forbids drivers from setting `FileID` via `DiscoveredItem.Columns`, and `DiscoverStage` (`packages/ContentPipeline/engine/src/stages/DiscoverStage.ts:51`) runs per `ContentSource` rather than per entity record. **Option C** is unsafe under `Content Pipeline — Sync` (`packages/ContentPipeline/engine/src/PipelineProcessor.ts:397–442`) unless coupled with a no-op driver, duplicates the fragile hand-rolled pattern in `BettyAdminResolver.BettyAdminAddContent` (`apps/MJAPI/src/resolvers/BettyAdminResolver.ts:2373–2597`), and leaves `DeleteStage.removeDurableCopy` able to delete shared `MJ: Files` rows. **Option D** is a non-starter for Collaboration: `AutotagCloudStorage.Discover` (`packages/ContentAutotagging/src/CloudStorage/providers/AutotagCloudStorage.ts:191–210`) leaves `EntityRecordDocumentID = NULL`, which causes Collaboration's RLS filters to hide every uploaded chunk from `UI` and `Space Participant` users while `SearchEngine.VerifyOriginRecords` (`packages/SearchEngine/src/generic/SearchEngine.ts:3261`, `3330`, `3414`) treats `EntityRecordDocumentID = NULL` as external content and passes it unconditionally (`if (origin === null) return true`), leaking `Team`-band and cross-space files to any role without those RLS filters.

## Baseline: How Collaboration Uploads, Retrieval, and Origin Filtering Work Today

Before comparing Options A–D against Questions 1–8, here is the verified code baseline in `bizapps-collaboration` and `MJ`:

1. **Upload path (`uploadSpaceFile`)**:
   - `uploadSpaceFile` (`packages/CoreEntitiesServer/src/upload-space-file.ts:150–233`) checks permissions (`canWriteSpace`, `canWriteLibrary`, `decideUploadBand` at `upload-space-file.ts:151–171`), stores the bytes via `request.store.put` (`collaborationFileStore` in `packages/CoreEntitiesServer/src/collaboration-file-store.ts:10–29`, which calls `FileStorageEngine.Instance.UploadFile` at `collaboration-file-store.ts:15–22` and creates an `MJ: Files` row with `ID = stored.fileId`), creates an `MJ: Artifacts` row and an `MJ: Artifact Versions` row (`writeArtifact` at `upload-space-file.ts:63–87` with `ContentMode = 'File'` and `FileID = stored.fileId` at `upload-space-file.ts:76–77`), and saves an `MJ_BizApps_Collaboration: Space Items` row (`upload-space-file.ts:199–206`) with:
     - `SpaceID = request.spaceId`
     - `EntityID = files.ID` (`MJ: Files`)
     - `RecordID = 'ID|' + stored.fileId`
     - `ArtifactVersionID = artifact.versionId`
     - `ConversationID = decision.conversationId`
     - `Band = decision.band` (`'General'` or `'Team'`)
2. **Retrieval path (`executeSpaceChatTurn` → `retrieveSpaceContext` → `SearchEngine.Instance.Search`)**:
   - `executeSpaceChatTurn` (`packages/CoreEntitiesServer/src/execute-space-chat-turn.ts:390–408`) resolves the room's search scope (`resolveSpaceAgentContext` in `packages/CoreEntitiesServer/src/resolve-space-agent-context.ts:27–38`: `'Collaboration: Space Reach (General)'` vs `'Collaboration: Space Reach (Team)'`) and calls `retrieveSpaceContext` (`packages/CoreEntitiesServer/src/space-agent-retrieval.ts:81–127`), which calls `SearchEngine.Instance.Search` (`space-agent-retrieval.ts:103–109`) as the calling `user`.
   - All three Collaboration search scopes (`metadata/search-scopes/.collaboration-search-scopes.json:1–107`) set `SourceTypes: ["entity", "storage", "fulltext", "vector"]` (`.collaboration-search-scopes.json:19, 50, 81`) and `EntityNames: ["MJ_BizApps_Collaboration: Space Items", "MJ_BizApps_Tasks: Tasks", "MJ: Content Items", "MJ: Content Item Chunks"]` (`.collaboration-search-scopes.json:21–26, 52–57, 83–88`).
   - When `MJ: Content Items` or `MJ: Content Item Chunks` rows return from `SearchEngine.Instance.Search`, `enrichContentHits` (`packages/CoreEntitiesServer/src/space-agent-retrieval.ts:321–393`) maps each chunk (`chunk.ContentItemID`) or item (`item.EntityRecordDocumentID`) through `MJ: Entity Record Documents` (`erd.EntityID`, `erd.RecordID`) back to the owning `SpaceItem` (matching either `SpaceItem.ID = bareId(erd.RecordID)` when `erd.EntityID` is `MJ_BizApps_Collaboration: Space Items`, or `SpaceItem.EntityID + '|' + bareId(SpaceItem.RecordID) = erd.EntityID + '|' + bareId(erd.RecordID)` when `erd.EntityID` is `MJ: Files` at `space-agent-retrieval.ts:352–363`), and then enforces `filterByReach` (`space-agent-retrieval.ts:116`, `253–268`) for room/subtree and `Band` (`General` vs `Team`).
3. **Two-gate security in `SearchEngine` and Collaboration RLS**:
   - **Gate 1 — Entity RLS (`admitOwnRows`)**: `SearchEngine.filterEntityResults` (`packages/SearchEngine/src/generic/SearchEngine.ts:2849–2889`) runs `admitOwnRows` (`SearchEngine.ts:2880`) via `RunViews` as `contextUser`. For `UI` and `Space Participant` roles (`metadata/entity-permissions/.entity-permissions.json:795, 810, 825`), SQL Server applies the three `"… In Reach"` RLS filters defined in `metadata/row-level-security-filters/.row-level-security-filters.json:422–451`:
     - `Collaboration: Entity Record Documents In Reach` (`.row-level-security-filters.json:424–431`): admits an `MJ: Entity Record Documents` row (`erd`) iff:
       1. `erd.EntityID = '41165FEC-A52B-469A-A880-3B108C39A65E'` (`MJ_BizApps_Collaboration: Space Items`) and `TRY_CAST(REPLACE(erd.RecordID, N'ID|', N'') AS UNIQUEIDENTIFIER)` is a `SpaceItem.ID` in a space where the user is an `Active` `SpaceParticipant` (or `OwnerUserID`) and `(si.Band = N'General' OR sm.SpaceRoleTypeID IN (... Coordinator / Team Member ...))`, **OR**
       2. `(CAST(erd.EntityID AS NVARCHAR(36)) + N'|' + REPLACE(erd.RecordID, N'ID|', N''))` matches `CAST(si.EntityID AS NVARCHAR(36)) + N'|' + REPLACE(si.RecordID, N'ID|', N'')` on a visible `SpaceItem` `si` (which matches `erd.EntityID = MJ: Files` and `erd.RecordID = 'ID|<fileId>'`!), **OR**
       3. `erd.EntityID = 'B348FFA2-B1A7-4AC2-B6FD-F4E0C0697466'` (`MJ_BizApps_Tasks: Tasks`) linked via `TaskLink` to a visible `SpaceItem`.
     - `Collaboration: Content Items In Reach` (`.row-level-security-filters.json:434–441`): admits an `MJ: Content Items` row iff `EntityRecordDocumentID IN (SELECT erd.ID ...)` or `RootParentID IN (SELECT root_ci.ID FROM [__mj].[vwContentItems] AS root_ci WHERE root_ci.EntityRecordDocumentID IN (SELECT erd.ID ...))`.

   - **Gate 2 — Origin verification (`VerifyOriginRecords`)**: `SearchEngine.VerifyOriginRecords` (`packages/SearchEngine/src/generic/SearchEngine.ts:3183–3199`, `3240–3456`) resolves each `MJ: Content Item Chunks` → `ContentItemID` (`lookupChunkItems` at `SearchEngine.ts:3272–3284`) → `EntityRecordDocumentID` (following `RootParentID` for split/archive children in `classifyItemRows` at `SearchEngine.ts:3324–3335`) → `MJ: Entity Record Documents` (`Entity`, `RecordID` in `lookupEntityRecordDocuments` at `SearchEngine.ts:3342–3351`), and runs `ReadableOriginRecordIDs` (`SearchEngine.ts:3430–3448`) via `RunViews` on the origin entity as `contextUser`.

### Option A — A First-Class `"Uploaded File"` `ContentSourceType` + Push-Ingest Helper in `@memberjunction/content-pipeline`

#### 1. What changes
- **MJ (`~/Projects/mjws-collab/MJ`)**:
  1. **Metadata (`metadata/content-source-types/.content-source-types.json`)**: Add one new `MJ: Content Source Types` record (`Name: "Uploaded File"`, `DriverClass: "UploadedFileSourceDriver"`, `Configuration: "{}"`) alongside the existing 7 types in `metadata/content-source-types/.content-source-types.json:1–188` (`Entity`, `Cloud Storage`, `Local File System`, `Website`, `RSS Feed`, `Web Page`, `API Feed`).
  2. **Driver (`packages/ContentPipeline/engine/src/`)**: Add a tiny `@RegisterClass(AutotagBase, 'UploadedFileSourceDriver')` subclass of `AutotagBase` (`packages/ContentAutotagging/src/Core/generic/AutotagBase.ts:15–64`) with `SupportsExhaustiveWalk = false` (`AutotagBase.ts:38`) and an empty `async *Discover(): AsyncIterable<DiscoveredItem> {}` generator (`AutotagBase.ts:45`).
  3. **Push-ingest / remove helper (`packages/ContentPipeline/engine/src/`)**: Export `IngestUploadedFile` and `RemoveUploadedFile` (or `ContentPipelineIngester.Ingest` / `Remove`) from `@memberjunction/content-pipeline` (`packages/ContentPipeline/engine/src/index.ts:1–23`):
     - `Ingest({ ContentSourceID, FileID, Origin?: { EntityID, RecordID }, Name?, Description?, URL?, RunImmediately?, ContextUser, Provider })`:
       - Loads the `MJ: Content Sources` row via `KnowledgeHubMetadataEngine.Instance.GetContentSourceByID` (`packages/ContentPipeline/engine/src/ContentSourceConfigurationResolver.ts:36–41`).
       - When `Origin` is supplied, finds or creates the `MJ: Entity Record Documents` row (`EntityID = Origin.EntityID`, `RecordID = Origin.RecordID`) — the same lookup/create pattern used in `AutotagEntity.upsertEntityRecordDocument` (`packages/ContentAutotagging/src/Entity/generic/AutotagEntity.ts:805–825`).
       - Finds or creates the `MJ: Content Items` row keyed by `(ContentSourceID, EntityRecordDocumentID)` or `(ContentSourceID, Checksum/URL)`, sets `FileID`, `EntityRecordDocumentID`, `ContentSourceID`, `ContentTypeID`, `ContentSourceTypeID`, `ContentFileTypeID`, `Name`, `Description`, `URL` (e.g., `file://${FileID}`), and sets `ExtractionStatus = 'Pending'`, `TaggingStatus = 'Pending'`, `SegmentationStatus = 'Pending'`, `EmbeddingStatus = 'Pending'`, `DeleteStatus = null`.
       - When `RunImmediately` is requested, runs `PipelineProcessor` (`packages/ContentPipeline/engine/src/PipelineProcessor.ts:55–91`) scoped to that `ContentItem.ID` through `Extract → Segment → Embed` (and optionally `Tag`).
     - `Remove({ ContentSourceID?, Origin?, FileID?, ContentItemID?, KeepFile?: true, RunImmediately?, ContextUser, Provider })`:
       - Locates the matching live `MJ: Content Items` row(s) (`DeleteStatus IS NULL`), **clears `item.FileID = null` and saves** when the file is caller-owned (`KeepFile !== false`) so `DeleteContentItemStage.removeDurableCopy` (`packages/ContentPipeline/engine/src/stages/DeleteStage.ts:116–152`) will not delete the caller's `MJ: Files` row, calls `MarkContentItemForDeletion(item.ID, provider, contextUser)` (`packages/ContentPipeline/engine/src/ContentPipelineDeleteMarker.ts:31–44`), and optionally runs `DeleteContentItemChunkStage` + `DeleteContentItemStage` (`packages/ContentPipeline/engine/src/stages/DeleteStage.ts:261–300`) immediately.
- **Collaboration (`~/Projects/mjws-collab/bizapps-collaboration`)**:
  1. **Metadata**: Add one `MJ: Content Sources` row (`Name: "Collaboration: Space Uploads"`, `ContentSourceTypeID: "@lookup:MJ: Content Source Types.Name=Uploaded File"`).
  2. **Upload hook (`packages/CoreEntitiesServer/src/upload-space-file.ts:199–232`)**: After `item.Save()` succeeds (`upload-space-file.ts:206`), call `IngestUploadedFile` with `FileID = stored.fileId` and `Origin = { EntityID: spaceItemsEntity.ID, RecordID: 'ID|' + item.ID }`.
  3. **Delete hook (`packages/CoreEntitiesServer/src/SpaceItemEntityServer.ts:390–406`)**: In `SpaceItemEntityServer.Delete`, before `super.Delete()` and `deleteVersionedArtifactAndFile` (`SpaceItemEntityServer.ts:461–505`), call `RemoveUploadedFile` for the `SpaceItem` origin so its `ContentItem` and `ContentItemChunk` rows (and vectors) are deleted without touching `MJ: Files` (which `deleteVersionedArtifactAndFile` owns).

#### 2. The origin link
- **How `EntityRecordDocumentID` is populated**:
  - `IngestUploadedFile` receives `Origin: { EntityID, RecordID }`.
  - Should `Origin` point at the `SpaceItem` (`EntityID = '41165FEC-A52B-469A-A880-3B108C39A65E'`, `RecordID = 'ID|' + spaceItem.ID`) or at `MJ: Files` (`EntityID = filesEntity.ID`, `RecordID = 'ID|' + stored.fileId`)?
  - **Both pass all Collaboration filters**, because `Collaboration: Entity Record Documents In Reach` (`metadata/row-level-security-filters/.row-level-security-filters.json:428–429`) and `enrichContentHits` (`packages/CoreEntitiesServer/src/space-agent-retrieval.ts:352–363`) explicitly accept **either**:
    1. `erd.EntityID = '41165FEC-A52B-469A-A880-3B108C39A65E'` (`MJ_BizApps_Collaboration: Space Items`) with `erd.RecordID = 'ID|' + spaceItem.ID`, **or**
    2. `erd.EntityID = filesEntity.ID` (`MJ: Files`) with `erd.RecordID = 'ID|' + fileId` (via the `CAST(erd.EntityID AS NVARCHAR(36)) + N'|' + REPLACE(erd.RecordID, N'ID|', N'')` branch at `.row-level-security-filters.json:429` and `space-agent-retrieval.ts:359–362`).
  - **However, pointing `Origin` at `MJ_BizApps_Collaboration: Space Items` (`EntityID = '41165FEC-A52B-469A-A880-3B108C39A65E'`, `RecordID = 'ID|' + spaceItem.ID`) is strictly better** for two code-verified reasons:
    1. **`SearchEngine.VerifyOriginRecords` (`packages/SearchEngine/src/generic/SearchEngine.ts:3430–3448`)**: `ReadableOriginRecordIDs` runs `RunViews` on the origin entity as `contextUser`. `MJ_BizApps_Collaboration: Space Items` has the `Collaboration: Space Items In Reach` RLS filter (`metadata/entity-permissions/.entity-permissions.json:525`), which enforces room membership and `General` vs `Team` band at the SQL level. By contrast, `MJ: Files` (`entity-permissions/.entity-permissions.json:835–855`) has **no** `ReadRLSFilterID` in Collaboration!
    2. **Archive/multi-file uploads (`ExtractStage.commitExpandedEntries`, `packages/ContentPipeline/engine/src/stages/ExtractStage.ts:462–538`)**: When a `.zip`, `.tar.gz`, or `.tgz` is uploaded, `ExtractStage` creates child `MJ: Content Items` rows with `ParentID = record.Identity.RecordID` (`ExtractStage.ts:505`), and SQL Server computes `RootParentID` on `vwContentItems`. Both `SearchEngine.classifyItemRows` (`SearchEngine.ts:3324–3335`) and Collaboration's RLS filters (`.row-level-security-filters.json:439, 449`) resolve `RootParentID → root_ci.EntityRecordDocumentID`, so every archive child and its `ContentItemChunk`s automatically inherit the `SpaceItem` origin!

#### 3. Discover and Sync
- **What `Content Pipeline — Discover` and `Content Pipeline — Sync` do**:
  - `Content Pipeline — Discover` (`metadata/record-processes/.content-pipeline.json:4–23`) runs `DiscoverStage` over `MJ: Content Sources` where `ForceDiscovery = 1` (`.content-pipeline.json:10`). Our `"Collaboration: Space Uploads"` source has `ForceDiscovery = 0`, so `Content Pipeline — Discover` never selects it. Even if someone sets `ForceDiscovery = 1`, `UploadedFileSourceDriver.Discover` yields 0 items (`Outcome.Complete('discovered 0 item(s)')` at `packages/ContentPipeline/engine/src/PipelineProcessor.ts:357–359`).
  - `Content Pipeline — Sync` (`metadata/record-processes/.content-pipeline.json:34–59`) selects `MJ: Content Sources` where `LastSyncedAt IS NULL OR LastSyncedAt < DATEADD(day, -30, GETUTCDATE())` (`.content-pipeline.json:37`) and runs `DiscoverStage` with `Options: { "Mode": "Sync" }` and `MaxSyncRemovalShare: 0.5`.
  - In `DiscoverStage.resolveWalkSource` (`packages/ContentPipeline/engine/src/stages/DiscoverStage.ts:118–121`), when `isSync` is true and `!driver.SupportsExhaustiveWalk`, `DiscoverStage` throws `FatalStageError("Driver 'UploadedFileSourceDriver' does not support exhaustive walks (SupportsExhaustiveWalk = false), so Sync mode cannot run against this source")`.
  - **Even cleaner**: in `PipelineProcessor.evaluateSyncWalk` (`packages/ContentPipeline/engine/src/PipelineProcessor.ts:397–411`) or `DiscoverStage.Run` (`DiscoverStage.ts:57–95`), when a driver has `SupportsExhaustiveWalk === false` (or `PushOnly === true`), `DiscoverStage` in `Sync` mode can return `Outcome.Skipped('push-only source; Sync does not walk')` so `Content Pipeline — Sync` does not log a fatal error every run on push-only sources, and **never** calls `reconcileSyncOrphans` (`PipelineProcessor.ts:414–442`).

#### 4. Delete and replace
- **What happens when a `Space Item` is deleted**:
  - Today, `SpaceItemEntityServer.Delete` (`packages/CoreEntitiesServer/src/SpaceItemEntityServer.ts:390–406`) deletes linked tasks/conversations, calls `super.Delete()`, and then calls `deleteVersionedArtifactAndFile` (`SpaceItemEntityServer.ts:461–505`), which checks `isFileStillReferenced` (`SpaceItemEntityServer.ts:423–437`) and, if no other `SpaceItem` points to that `FileID`, deletes the `MJ: Artifact Versions` row, the `MJ: Artifacts` row, the storage blob (`FileStorageEngine.Instance.DeleteFile`), and the `MJ: Files` row (`SpaceItemEntityServer.ts:474–499`).
  - **Critical hazard in `DeleteContentItemStage.removeDurableCopy` (`packages/ContentPipeline/engine/src/stages/DeleteStage.ts:116–152`)**:
    - When `MarkContentItemForDeletion` (`packages/ContentPipeline/engine/src/ContentPipelineDeleteMarker.ts:31–44`) marks a `Content Item` and its `Content Item Chunks` with `DeleteStatus = 'Pending'`, `DeleteContentItemStage` (`DeleteStage.ts:281–300`) runs `BaseDeleteStage.Run` (`DeleteStage.ts:57–83`).
    - At `DeleteStage.ts:74`, `BaseDeleteStage.Run` calls `await this.removeDurableCopy(record, context)`.
    - `removeDurableCopy` (`DeleteStage.ts:116–152`) reads `Pipeline.fileID` (hydrated from `ContentItem.FileID` at `packages/ContentPipeline/engine/src/WorkingRecordHydrator.ts:27`), loads the `MJ: Files` row, **deletes the object from storage** (`resolved.Driver.DeleteObject` at `DeleteStage.ts:138`), clears `ContentItem.FileID = null` (`DeleteStage.ts:139`), and **deletes the `MJ: Files` row** (`await file.Delete()` at `DeleteStage.ts:141`)!

- **What happens when a file is replaced (re-uploaded)**:

- **How stages are triggered**:

Because `SegmentStage` does not depend on `TagStage` (`TagStage.ts:44`: `"Independent of Segment: both read the same text, in either order"`), `IngestUploadedFile` can run `Extract → Segment → Embed` synchronously on upload (~100–600 ms) so the file is immediately searchable in the very next chat turn, while leaving `TaggingStatus = 'Pending'` (or running `Tag` asynchronously in the background).

    - If `ContentSourceType` is `Web Page`, `RSS Feed`, or `Website` (`AutotagWebsite`, `SupportsExhaustiveWalk = false` by default on `AutotagBase` at `packages/ContentAutotagging/src/Core/generic/AutotagBase.ts:38`): `DiscoverStage.resolveWalkSource` (`DiscoverStage.ts:118–121`) throws `FatalStageError("Driver 'AutotagWebsite' does not support exhaustive walks (SupportsExhaustiveWalk = false), so Sync mode cannot run against this source")`. That prevents orphan deletion, **but** if someone ever sets `ForceDiscovery = 1` or runs `Discover`, `AutotagWebsite` will try to crawl `ContentSource.URL`!
    - If `ContentSourceType` is `Entity` (`AutotagEntity`, `SupportsExhaustiveWalk = true` at `packages/ContentAutotagging/src/Entity/generic/AutotagEntity.ts:532`) or `Cloud Storage` (`AutotagCloudStorage`, `SupportsExhaustiveWalk = true` at `packages/ContentAutotagging/src/CloudStorage/providers/AutotagCloudStorage.ts:185`):
      - If unconfigured, the driver throws during `Sync`.
      - If configured to return `0` items when live uploaded items exist, `PipelineProcessor.reconcileSyncOrphans` (`packages/ContentPipeline/engine/src/PipelineProcessor.ts:414–421`) returns `Outcome.Fatal("Sync walk returned 0 items while N live item(s) exist...")`.
      - If it yields some items whose `URL`s do not match the uploaded items' `URL`s (`PipelineProcessor.ts:403–409`), and the uploaded items are `<= 50%` of the source (`MaxSyncRemovalShare = 0.5` at `.content-pipeline.json:51` and `PipelineProcessor.ts:422–432`), `markOrphansForDeletion` (`PipelineProcessor.ts:435, 437–442`) **marks the uploaded items `DeleteStatus = 'Pending'`**!

#### 4. Delete and replace
- **Delete**: Same `DeleteContentItemStage.removeDurableCopy` (`packages/ContentPipeline/engine/src/stages/DeleteStage.ts:116–152`) trap as Option A: Collaboration's delete helper **must** set `ContentItem.FileID = null` and save before calling `MarkContentItemForDeletion`, or else `DeleteContentItemStage` will delete the `MJ: Files` row and storage object out from under `MJ: Artifact Versions` and `SpaceItemEntityServer.deleteVersionedArtifactAndFile` (`packages/CoreEntitiesServer/src/SpaceItemEntityServer.ts:461–505`).
- **Replace**: Collaboration's helper must manually look up the existing `MJ: Content Items` row for that `EntityRecordDocumentID`, update `FileID`, set `ExtractionStatus = 'Pending'`, and re-run `PipelineProcessor`.

#### 5. Time to searchable
- Same as Option A (~100–600 ms for `Extract → Segment → Embed` when Collaboration invokes `PipelineProcessor` in-process for that `ContentItem.ID`, or delayed until the next scheduled `Content Pipeline — Ingest` run if it only saves the row).

#### 6. Reuse
- **None**: The helper lives inside `@mj-biz-apps/collaboration-core-entities-server`.
- Betty already has two copies of this exact workaround (`BettyAdminResolver.BettyAdminAddContent` in `apps/MJAPI/src/resolvers/BettyAdminResolver.ts:2373–2597` and `CreateFeedbackContent` in `packages/BettyLib/src/feedbackContent.ts:136–277`), and Option C would create a **third** app-local copy in Collaboration instead of putting the 150-line primitive in `@memberjunction/content-pipeline`.

#### 7. Fit with MJ
- **Poor fit**: Violates the "Use MJ; don't work around it" principle in `plans/uploads-to-content-pipeline.md:20–24`. It requires squatting on an unrelated `ContentSourceType` (`Entity` or `Web Page`), relies on `SupportsExhaustiveWalk = false` throwing a `FatalStageError` to survive `Content Pipeline — Sync`, and forces Collaboration to know internal details of `WorkingRecordHydrator` (`FileID` → `Pipeline.fileID`) and `DeleteStage.removeDurableCopy`.

#### 8. Risks and open questions
- Any future change to `WorkingRecordHydrator`, `WorkingRecordCommitter`, or `DeleteStage` in `@memberjunction/content-pipeline` could silently break Collaboration's hand-rolled row setup because no MJ contract or test covers externally inserted `MJ: Content Items` rows on a borrowed `ContentSourceType`.
- Same `EmbedStage` vs `SimpleVectorServiceProvider` (`IsReadOnly = true`) issue described in Option A Question 8.

### Option D — Point a `Cloud Storage` `ContentSource` at Collaboration's Upload Folder

#### 1. What changes
- **MJ (`~/Projects/mjws-collab/MJ`)**: None.
- **Collaboration (`~/Projects/mjws-collab/bizapps-collaboration`)**:
  - Seed one `MJ: Content Sources` row with `ContentSourceTypeID = 'B131763E-F36B-1410-8DB0-00021F8B792E'` (`Cloud Storage`, `metadata/content-source-types/.content-source-types.json:24–54`) and `CloudStorageAccountID = '2B8346EE-2065-4E34-9431-85C6C72E443B'` (`COLLABORATION_STORAGE_ACCOUNT_ID`).
  - After `uploadSpaceFile` (`packages/CoreEntitiesServer/src/upload-space-file.ts:150–233`), trigger `Content Pipeline — Discover` followed by `Content Pipeline — Ingest`.

#### 2. The origin link
- **CONFIRMED: `Cloud Storage` items carry NO origin link (`EntityRecordDocumentID = NULL`), which completely breaks Collaboration's security model.**
  - **Evidence in `AutotagCloudStorage`**:
    - `AutotagCloudStorage.Discover` (`packages/ContentAutotagging/src/CloudStorage/providers/AutotagCloudStorage.ts:191–210`) lists objects in the storage provider via `provider.ListObjects(pathPrefix, '/')` (`AutotagCloudStorage.ts:396`) and yields `DiscoveredItem` records containing only `URL: object.fullPath` and `Fields: [Title, Date, FileType]` (`AutotagCloudStorage.ts:199–208`).
    - When `WorkingRecordCommitter.commitDiscoveredItem` (`packages/ContentPipeline/engine/src/WorkingRecordCommitter.ts:127–168`) saves the `MJ: Content Items` row, **`EntityRecordDocumentID` is left `NULL`** (and `FileID` is only created if `ExtractStage.persistDurableCopy` at `packages/ContentPipeline/engine/src/stages/ExtractStage.ts:550–614` writes a *second* copy of the blob back into `MJ: Files`!).
  - **What happens in Collaboration when `EntityRecordDocumentID IS NULL`?**
    1. **For `UI` and `Space Participant` roles (RLS active)**:
       - `Collaboration: Content Items In Reach` (`metadata/row-level-security-filters/.row-level-security-filters.json:439`) requires:
         `([EntityRecordDocumentID] IN (SELECT erd.ID ...) OR [RootParentID] IN (SELECT root_ci.ID FROM [__mj].[vwContentItems] AS root_ci WHERE root_ci.EntityRecordDocumentID IN (SELECT erd.ID ...)))`.
       - `Collaboration: Content Item Chunks In Reach` (`.row-level-security-filters.json:449`) requires the parent `ContentItem` to satisfy the same `EntityRecordDocumentID` check.
       - Because `EntityRecordDocumentID IS NULL` and `RootParentID IS NULL`, **SQL Server's RLS filter rejects 100% of `Cloud Storage` `MJ: Content Items` and `MJ: Content Item Chunks` rows for `UI` and `Space Participant` users!**
       - Even if a row somehow reached `enrichContentHits` (`packages/CoreEntitiesServer/src/space-agent-retrieval.ts:321–393`), `enrichContentHits` drops any hit that cannot be mapped via `item.EntityRecordDocumentID` (`space-agent-retrieval.ts:346, 369`) to a `SpaceItem` in `reach` (`space-agent-retrieval.ts:386`: `if (!spaceItem) continue;`)!
    2. **For roles without RLS (e.g., `Developer`, `Integration`) or if RLS were relaxed to allow `EntityRecordDocumentID IS NULL`**:
       - Look at `SearchEngine.resolveContentOrigins` (`packages/SearchEngine/src/generic/SearchEngine.ts:3261`), `classifyItemRows` (`SearchEngine.ts:3330`), and `keepReadableOrigins` (`SearchEngine.ts:3413–3418`):
         ```ts
         // SearchEngine.ts:3330
         if (!row.ParentID) map.set(id, null);
         // SearchEngine.ts:3261 — external content: no origin
         origins.set(id, null);
         // SearchEngine.ts:3414
         if (origin === null) return true;
         ```
       - **`SearchEngine.VerifyOriginRecords` passes every item with `EntityRecordDocumentID = null` unconditionally!**
       - And because `collaborationFileStore` (`packages/CoreEntitiesServer/src/collaboration-file-store.ts:15–22`) uploads all files across every space and every band (`General` and `Team`) into the same storage account without per-space or per-band isolation, **every `Team`-band file and every file from private/sealed spaces would leak across all spaces and conversations**!

#### 3. Discover and Sync
- `AutotagCloudStorage.SupportsExhaustiveWalk` is `true` (`packages/ContentAutotagging/src/CloudStorage/providers/AutotagCloudStorage.ts:185`).
- `Discover` and `Sync` walk the entire storage prefix recursively (`crawlStorageProvider` at `AutotagCloudStorage.ts:390–409`), which scales poorly as total uploads grow across all spaces.

#### 4. Delete and replace
- If a user deletes a `Space Item` whose `FileID` is still referenced by another `Space Item` (`isFileStillReferenced` at `packages/CoreEntitiesServer/src/SpaceItemEntityServer.ts:423–437`), the blob stays in storage, so `AutotagCloudStorage` keeps the `ContentItem` alive.
- Conversely, if `ExtractStage.persistDurableCopy` (`packages/ContentPipeline/engine/src/stages/ExtractStage.ts:550–614`) is enabled (`StoreContentItemFile = true`), `ExtractStage` writes a duplicate `MJ: Files` row and blob for every discovered file!

#### 5. Time to searchable
- Slowest of all options: requires listing the cloud storage bucket (`AutotagCloudStorage.Discover` at `AutotagCloudStorage.ts:191–210`), then fetching the bytes back out of storage via `AutotagCloudStorage.Fetch` (`AutotagCloudStorage.ts:212–217`) instead of reading `ContentItem.FileID` directly.

#### 6. Reuse
- Only usable for public or organization-wide document buckets where individual files do not have per-space, per-room, or per-record (`General` vs `Team` band) access control.

#### 7. Fit with MJ
- `AutotagCloudStorage` is the right driver for crawling an external S3/Azure/GCS bucket of shared documents, **not** for indexing application-managed uploads that already have `MJ: Files` rows (`FileID`) and per-record permissions (`MJ: Entity Record Documents`).

#### 8. Risks and open questions
- **Disqualifying security and correctness failure**: Either hides all uploaded content (under Collaboration's RLS filters and `enrichContentHits`) or leaks `Team`-band and cross-space files (under `SearchEngine.VerifyOriginRecords`'s `origin === null` bypass).
